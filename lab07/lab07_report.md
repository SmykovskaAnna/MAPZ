## 1. Мета роботи

Навчитися формально описувати стан і поведінку програмної системи мовами Z та VDM-SL, формулювати інваріанти й передумови операцій, а також перевіряти відповідність формальної моделі попереднім UML-діаграмам.

## 2. Основні правила

| Код | Правило |
|---|---|
| П1 | Запис виконання пов’язаний з однією звичкою та одним періодом. |
| П2 | Для пари «звичка–період» є не більше одного запису (ліміт 1); ID запису не повторюється. |
| П3 | Виконання можна позначити лише для наявної звички у стані «Очікує». |
| П4 | Стан «Виконано» означає, що для поточного періоду існує запис. |
| П5 | Пауза зберігає активний стан, з якого звичку призупинили. |
| П6 | Після виконаного періоду можна перейти до нового; архівовану звичку можна відновити з новим періодом. |
| П7 | Архівувати можна звичку в активному стані. |

Правило BR2 задане структурно: у Z записи - часткова функція від пари "звичка, період" до ідентифікатора запису. У VDM-SL використана мапа з таким самим ключем.

## 3. Z-специфікація

Файл [Лаб7_специфікація_Z.txt](Лаб7_специфікація_Z.txt) містить три базові типи, вільні типи стану й результату, аксіоматичну константу `максЗаписівЗаПеріод = 1`, схему стану з чотирма змінними та інваріантами, початковий стан, операції `Δ` і запит `Ξ`.

Повна операція `ПозначитиВиконаноюПовна` визначена об’єднанням успішної схеми та п’яти схем помилок. Кожна схема має однакові вхідні й вихідні змінні; помилкові схеми використовують `ΞHabitTracker`, тому не змінюють стан.

## 4. Передумова та перевірка інваріанта

Успішна передумова `ПозначитиВиконаною(h?,r?,p?)`:

`h? ∈ dom стан ∧ стан(h?) = очікує ∧ p? = період(h?) ∧ (h?,p?) ∉ dom записи ∧ r? ∉ ran записи`.

Наявність звички потрібна для доступу до її стану й періоду; стан `очікує` дозволяє цей перехід; період має бути поточним; пара ще не повинна мати запису; ID нового запису має бути вільним.

**Початковий стан:** усі мапи порожні, тому області `стан` і `період` збігаються, а умови про записи та паузу виконуються.

**`ПозначитиВиконаною`:** передумова забезпечує наявну звичку й період та невикористані пару й ID. Операція додає цю пару до часткової ін’єкції та переводить статус у `виконано`; отже, інваріант виконаного стану зберігається.

**`Відновити`:** звичка повертається до збереженого активного стану, а її ID вилучається з `доПаузи`. Решта змінних не змінюється, тож відповідність між станом паузи й `доПаузи` зберігається.

Це ручні обґрунтування; автоматичне доведення не запускалося.

## 5. VDM-SL

Файл [Лаб7_специфікація.vdmsl](Лаб7_специфікація.vdmsl) описує той самий фрагмент: базові типи ID, типи стану, `Progress` з інваріантом `0..100`, стан із чотирма змінними, інваріант і `init`. Функція `прогрес` явна, `виконана` неявна. Операції мають `pre` і `post`; `ПозначитиВиконаною` відповідає операції Z. Також визначені створення, активація, новий період, пауза, відновлення, архівування й відновлення з архіву.

## 6. Простежуваність бізнес-правил

| Бізнес-правило | Z | VDM-SL | UML-модель ЛР2 / ЛР5 |
|---|---|---|---|
| П1: запис пов’язаний зі звичкою й періодом | Ключ `записи: (HABIT_ID × PERIOD_ID) ⤔ RECORD_ID` | `records: inmap RecordKey to RecordId` | ЛР2: композиція `Звичка 1 *-- 0..* ЗаписВиконання`; дата запису |
| П2: максимум один запис, ID не повторюється | Часткова ін’єкція `⤔`; константа `максЗаписівЗаПеріод=1` | `inmap`; передумова забороняє ID з `rng records` | ЛР2: композиція є, точний ліміт на період не заданий |
| П3: виконання лише зі стану очікування | Передумова `ПозначитиВиконаною` | `pre` `ПозначитиВиконаною` | ЛР5: `Очікує → Виконано`; ЛР2: `позначитиВиконаною()` |
| П4: виконаний стан має запис | Інваріант для поточного періоду | Інваріант `status` / `records` | ЛР5: перехід за наявності запису; ЛР2: `виконано: boolean` |
| П5: пауза зберігає активний стан | `доПаузи`, `Призупинити`, `Відновити` | `pausedFrom`, `Призупинити`, `Відновити` | ЛР5: повернення через історичний стан `H` |
| П6: новий період і повернення з архіву | `НовийПеріод`, `ВідновитиЗАрхіву` | `НовийПеріод`, `ВідновитиЗАрхіву` | ЛР5: `Період виконано → Очікує`; `Архівована → Активна` |
| П7: архівується активна звичка | Передумова `Архівувати` | `pre` `Архівувати` | ЛР5: активна звичка переходить до `Архівована` |

## 7. Відповідність специфікації діаграмі класів

| Формальний елемент | Клас ЛР2 | Відповідність |
|---|---|---|
| `HABIT_ID`, `status`, `period` | `Звичка` | Ідентифікатор, статус і формалізований поточний період |
| `RECORD_ID`, ключ `(звичка, період)` | `ЗаписВиконання` | ID та дата/період запису |
| `records` | Композиція `Звичка`—`ЗаписВиконання` | Задає зв’язок запису з конкретною звичкою і періодом |
| Створення, активація, пауза, архів | `Звичка` | `створити()` є в ЛР2; окремі методи переходів треба додати |
| Фіксація виконання | `ЗаписВиконання` | Відповідає `позначитиВиконаною()` |
| Прогрес | `Звичка` | Відповідає `отриматиПрогрес(): double`; формальна модель спрощує значення до 0% або 100% |

**Розбіжність з UML:** у ЛР2 статус має тип `String`, а в ЛР5 стани перелічені окремо. У формальній моделі статус типізований; також додані поточний період і збереження стану до паузи, яких у ЛР2 немає.

## 8. Неоднозначності

1. Межі календарного періоду не визначені. Прийнято задавати його абстрактним `PERIOD_ID`, а конкретні межі залишити застосунку.
2. ЛР5 не розписує паузу для кожної підстани активної звички. Прийнято зберігати й відновлювати `Очікує` або `Виконано`.
3. Для повернення з архіву підстан не уточнено. Прийнято починати новий період у стані очікування, зберігаючи старі записи.
